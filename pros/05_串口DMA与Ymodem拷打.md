# 05 串口 DMA、Ymodem 协议与 RS485 拷打

> 通信链路是嵌入式面试的另一高频区。代码依据：`Driver/SYSTEM/usart.c`（302 行）、`User/ymodem_protocol.c`（749 行）、`Driver/BSP/RS485.c`。

---

## 5.0 速记：串口与 Ymodem 关键点

- USART1：115200-8-N-1；**DMA2_Stream5_Ch4 循环模式**接收（缓冲 1024B）+ **IDLE 空闲中断**判帧结束
- ISR（抢占优先级 6）：读 SR→读 DR 清标志 → 停 DMA 算 received_len → 重启 DMA → `vTaskNotifyGiveFromISR(vUART1TaskHandle)`
- vUART1Task（优先级 4）：`ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` 阻塞 → 转发数据到 ymodem_rx_queue(256B) 和 lcd_display_queue
- 命令行：help / ls / cd / pwd / get / settime / exit（Ymodem_Task 解析，优先级 3）
- Ymodem 帧：SOH=128B 包、STX=1024B 包、EOT 结束、ACK 0x06、NAK 0x15、CAN 0x18、'C' 请求 CRC 模式
- CRC16：Xmodem 变体（初值 0x0000、查表、高字节先发）；数据包序号从 1 开始、每包 seq 取反校验；失败重试 10 次
- RS485：USART3 + 收发方向控制引脚（RE/DE），DMA Normal 模式 + 空闲中断，默认接收态

## Q5.1 为什么串口接收要用 DMA + 空闲中断？逐字节中断不行吗？

### 答题要点

1. **逐字节中断的问题**：115200 波特率下每字节间隔约 87μs，每个字节进一次中断做压栈/出栈/取数，长帧（Ymodem 1024B 数据包）会产生上千次中断，CPU 占用高且打断高频任务（CAN 收包）。
2. **DMA 循环接收**：硬件自动把收到的字节连续搬进 dma_rx_buffer[1024]，CPU 完全不参与数据搬运，只在一帧结束时处理。
3. **空闲中断判帧**：USART 的 IDLE 标志在"总线空闲超 1 字节时间"时置位，天然是"变长帧结束"信号——不需要自定义协议头/长度字段（本项目命令和 Ymodem 数据包长度都不固定）。
4. **任务通知收尾**：ISR 里算好 received_len、重启 DMA、通知 vUART1Task；任务侧一次性处理整帧。CPU 每帧只被唤醒一次。

### 追问：为什么用任务通知而不是信号量/队列？在这里的优势？

> 单生产者（USART1_IRQHandler）单消费者（vUART1Task），正是任务通知最佳场景：无额外控制块内存、零数据拷贝（数据本来就在 DMA 缓冲区里，通知只是"唤醒"信号）、速度快。如果多个任务都要消费串口数据才需要换成队列分发。

## Q5.2 ISR 里 received_len 怎么算出来的？DMA 计数器在循环模式下怎么理解？

### 答题要点（usart.c USART1_IRQHandler 193~199 行）

```c
DMA_Cmd(DMA2_Stream5, DISABLE);                    // 先停 DMA
received_len = DMA_RX_BUFFER_SIZE - DMA_GetCurrDataCounter(DMA2_Stream5); // 已搬了多少
DMA_SetCurrDataCounter(DMA2_Stream5, DMA_RX_BUFFER_SIZE); // 重置计数器
DMA_Cmd(DMA2_Stream5, ENABLE);                     // 重启，继续收下一帧
```

- DMA 循环模式：计数器从 1024 递减到 0 后自动回卷到 1024，内存写指针也回卷到缓冲首地址——等价于一个硬件环形缓冲。
- "已接收字节数 = 总大小 − 当前计数器值"是循环模式的标准算法。
- 为什么先停 DMA 再读计数器：防止读计数器的瞬间又有新字节搬入导致读数不准（竞态）；算完立即重启，停的时间窗口 ≈ 几个 μs，115200 下不会丢数据（一个字节 87μs，重启窗口远小于一个字节时间）。

### 追问：为什么清 IDLE 标志要先读 SR 再读 DR？

> STM32 手册规定：清除 IDLE 标志的办法是"先读 USART_SR，再读 USART_DR"。只读 SR 或只清其他标志都不行。代码里 `volatile uint32_t tmp = USART1->SR; tmp = USART1->DR;` 用 volatile 防止编译器优化掉这两个"看似无用"的读操作——这是很多新手踩过的坑（编译器把读 SR/DR 优化掉 → 标志清不掉 → 死循环进中断）。

## Q5.3 printf 是怎么重定向到串口的？为什么要禁用半主机？

### 答题要点（usart.c 41~91 行）

- 半主机（Semihosting）：ARM 调试器提供的一种机制，printf 等标准 I/O 通过断点指令把字符交给调试器显示。**脱离调试器运行时程序会卡死**（BKPT 无人响应）。
- 项目做法：`__use_no_semihosting`（AC5 用 pragma、AC6 用 __asm 声明）禁用半主机，重写 `fputc` 把每个字符轮询发送到 USART1：
  ```c
  int fputc(int ch, FILE *f) {
      while ((USART1->SR & 0X40) == 0);  // 等 TXE（发送缓冲区空）
      USART1->DR = (uint8_t)ch;
      return ch;
  }
  ```
- 同时要提供 `_ttywrch`、`_sys_exit`、`_sys_command_string` 三个桩函数避免链接错误；工程选项勾选 MicroLIB。
- 轮询 fputc 的代价：printf 一条长日志期间任务被阻塞，所以调试打印要节制（项目里大部分 printf 已注释掉）。

### 追问：fputc 用轮询等 TXE，为什么不用发送中断 + 缓冲？

> 简单优先：调试输出量小，轮询实现 3 行代码、无缓冲区管理；若改成中断发送需要环形发送缓冲 + 发送完成中断管理，收益仅在"大流量调试日志"场景。且本项目的关键数据走 CAN/SD 而非串口打印，串口主要是命令交互。

## Q5.4 Ymodem 协议讲一下：帧格式、传输流程、和 Xmodem 的区别

### 答题要点（ymodem_protocol.c 的实现 + 协议本身）

**帧格式：**
- 数据包：`[SOH/STX][seq][~seq][数据(128/1024B)][CRC16 高字节][CRC16 低字节]`
  - SOH(0x01)=128 字节包，STX(0x02)=1024 字节包；seq 从 1 起，每包加 1，到 255 回卷；`~seq` 用于校验；不足 128/1024 的数据区补 0（本项目发数据时实际用 SOH 发 128B 小块、用 STX 发 1024B 大块）。
- 控制字符：ACK(0x06) 正确、NAK(0x15) 请求重传、CAN(0x18) 取消、EOT(0x04) 传输结束、'C'(0x43) 接收方请求 CRC 模式。
- 0 号包：**文件信息包**（文件名\0文件大小\0 填充），Ymodem 特有，Xmodem 没有。

**传输流程（项目 Ymodem_SendFile 303~428 行）：**
1. 等待接收方发 'C'（CRC 模式）或 NAK（30 秒超时）；
2. 发 0 号文件信息包，等 ACK（重试 10 次）；
3. 依次发数据包 seq=1,2,3…，每包等 ACK，NAK 重传、CAN 中止；
4. 发 EOT 等 ACK → 再发一次 EOT 等 ACK → 接收方回 'C' 表示还要下一个文件；
5. 发全 0 的空 0 号包表示"没有更多文件"，等最终 ACK，传输结束。

**与 Xmodem 的区别：** Xmodem 只有 128B 包、无文件信息包、无批量文件、只有累加和校验；Ymodem 支持 1024B 包（1KB 模式）、0 号文件信息包、CRC16、多文件连续传输、支持取消（CAN）。

### 追问：为什么 EOT 要发两次？

> 协议规定：第一次 EOT 后接收方回 ACK；发送方再发一次 EOT，接收方回 'C' 表示"期待下一个文件"。这是 Ymodem 多文件机制的体现——单文件传输也要走完这套握手。代码里两次 EOT 之间加了 200ms delay，是兼容 Xshell 等终端工具的实测经验（去掉会偶发握手失败）。

### 追问：CRC16 参数？为什么高字节先发？

> Ymodem 用 CRC-16/XMODEM 变体：多项式 0x1021、初值 0x0000、不反转、无输出异或，查表实现（crc16_table[256]）。协议规定 CRC 高字节在前发送（大端），代码里 `crc_bytes[2] = {(crc >> 8) & 0xFF, crc & 0xFF}`。

## Q5.5 你的 Ymodem 是"发送方"实现，怎么和 SD 卡配合的？锁是怎么管理的？

### 答题要点

- 应用形态：设备是**日志文件提供方**（get 命令触发 Ymodem_SendFile 把 SD 卡里的 CSV 发给 PC），PC 端用 Xshell 的"接收 Ymodem"。
- 命令行入口：Ymodem_Task 逐字符组命令 → Ymodem_ProcessCommand → get 解析出文件名 → Ymodem_SendFile。
- **锁的粒度设计**（重点）：
  1. 打开文件读大小阶段：持 xSDCardMutex；
  2. **等待接收方 'C' 的 30 秒窗口：主动释放互斥量**——这期间 SD 写日志任务照常工作，不被"还没开始的传输"饿死；
  3. 发送数据阶段：重新获取互斥量，f_read 逐 1KB 读卡发送；
  4. 结束：f_close + Give。
- 为什么不能全程持锁：30 秒等握手期间持锁会让日志写入停 30 秒，SD 写队列（深度 3）早被憋满丢日志。

### 追问：Ymodem 传输和 CAN 日志记录同时进行，SD 总线够用吗？

> SD 总线由互斥量串行化，Ymodem 读卡和日志写卡交替进行。115200 串口 ≈ 11.5KB/s，SD 读卡速度 >1MB/s，读一个 1KB 包只需亚毫秒级占用，日志写入影响极小。实测传输中无丢帧告警。

## Q5.6 RS485 和 UART 的区别？你的 RS485 驱动要注意什么？

### 答题要点

- 电气层区别：RS485 是差分半双工总线（A/B 线），可多机挂一条总线（最多 32/128 节点）、抗干扰强、传输距离长（1200m@100kbps）；UART 是单端全双工点对点。
- **半双工的核心：收发方向控制**——RS485 收发器有 RE（接收使能）和 DE（发送使能）引脚，同一时刻只能一个方向。项目里 RS485_RE_PIN 控制，宏 RS485_RX_EN()/RS485_TX_EN() 切换，**默认置接收态**。
- 发送时序陷阱：先拉 DE 再发数据、数据发完（等 TC 传输完成标志，不是 TXE！）再拉回 RE，否则最后一字节会被截断。TXE 只表示"数据从移位寄存器→发送寄存器搬完"，TC 才表示"真正从引脚发完"。
- 项目里 RS485 初始化用 USART3 + DMA 接收 + 空闲中断（类似 USART1 的框架），波特率 9600。
- 半双工所以没有硬件流控，协议层要自己约定"一问一答"避免两个节点同时发（多机冲突）。

### 追问：RS485 总线上多个设备同时发送会怎样？怎么避免？

> 电平冲突导致数据全部错误（差分信号打架），且没有 CAN 那样的仲裁机制。解决靠协议：主从轮询（主机点名从机才应答）、或 CSMA 式"先听后发"。本项目 RS485 是预留接口，实际主链路是 CAN。

## 面试官可能挖的坑（本专题防翻车清单）

1. **"received_len 为什么要 DMA_RX_BUFFER_SIZE 减计数器？"** → 循环模式计数器是"剩余未搬字节数"，已搬 = 总大小 − 剩余。答成"直接读计数器"就翻车。
2. **"IDLE 中断每帧都触发吗？"** → 每帧结束触发一次；连续发数据中间没有空闲就不会触发，直到发完最后一个字节后的 1 字节空闲时间。若两帧间隔 <1 字节时间，会合并成一帧（协议层要能容忍）。
3. **"Ymodem 序号回卷怎么处理？"** → seq 是 uint8_t，255 之后回卷到 0 继续（协议定义如此，项目 YMODEM_PACKET_SEQ_MAX=0xFF 只是常量标记）。~seq 校验让回卷也可靠。
4. **"为什么 UART_Receive 里 xQueueReceive 用 10ms 超时而不是 portMAX_DELAY？"** → 为了支持总超时：外层 while 循环每 10ms 检查一次总耗时是否超 timeout，超时就中断接收返回。这是"带总超时的分片等待"模式。
5. **"发 1024 包还是 128 包？"** → 代码逻辑：`len <= 128 ? SOH : STX`，数据量 >128 字节用 1024 包，最后一包不足 1024 补 0 填充。面试官可能追问"小于 128 时用 SOH 的收益"——省 896 字节传输量。
6. **"你测过丢包吗？"** → 建议答：Xshell/Xmodem 实测大文件传输通过 CRC 校验；中途 CAN 满载 + Ymodem 同时跑未复现丢帧（队列告警机制可观察）。
7. **"为什么 lcd_display_queue 也要收到串口数据？"** → 用户敲的命令要回显在 LCD 上（本地也能看到交互），所以 vUART1Task 把数据同时投递给 ymodem 队列和 LCD 队列。
