## Q6.1 讲一下你的低功耗设计（VBAT 检测 + Standby）

### 答题要点（power_mgmt.c）

1. **电压检测**：ADC1 通道 18（内部 VBAT 通道），12 位、采样 480 周期。STM32 的 VBAT 通道内部有 **1/2 分压**，所以换算 `vbat_mv = adc_value × 3300 × 2 / 4095`。
2. **检测时机**：LED 软件定时器回调（500ms 周期）里顺手读一次电压——不额外开任务/定时器，"搭便车"检测。
3. **判定**：`vbat_voltage < VBAT_LOW_THRESHOLD(3200mV)` 且 low_battery_flag 防重入 → 打印告警 → 延时 100ms 让串口发完 → enter_low_power_mode()。
4. **进入 Standby 前**：关 LCD 背光、关显示；`PWR_WakeUpPinCmd(ENABLE)` 使能 WKUP 引脚；**必须 `PWR_ClearFlag(PWR_FLAG_WU | PWR_FLAG_SB)`**（不清标志进不去 Standby，这是经典坑）。
5. **模式选择**：注释里保留了 STOP 模式（保留 SRAM、中断可唤醒），实际选了 **Standby**（最低功耗，仅 WKUP/RTC 可唤醒，醒来等价于复位，重新跑 main）。理由：设备无人值守，彻底断电式待机最省电。
6. **唤醒后**：WKUP 引脚唤醒 → 芯片复位 → main 重新初始化（备份寄存器里可存"因低功耗唤醒"标记做差异化流程，当前未实现）。

### 追问：STOP 和 Standby 的区别？为什么选 Standby？

> STOP：内核停止但 SRAM/寄存器保留，任意 EXTI 中断可唤醒，恢复快，功耗 μA 级~几十 μA；Standby：SRAM 全丢、只有 WKUP/RTC 能唤醒，唤醒即复位，功耗最低（μA 级以下）。本项目掉电保护对象是"SD 卡里已落盘的数据"，RAM 里最多 512B 未刷盘缓冲，丢了可接受，所以选更省电的 Standby。

### 追问：ADC 采样为什么 480 周期？

> VBAT 内部通道带分压电阻，输入阻抗高，需要长采样时间才能充到 12 位精度；480 周期是手册推荐量级。采样时间短会导致读数偏低、跳动。

## Q6.2 按键扫描状态机讲讲？消抖怎么做的？

### 答题要点（app.c vKeyScanTask + LedKeyBeep.h）

**状态机（4 态）：**
```
IDLE ──按下──▶ PRESSED ──长按计时到(800ms)──▶ 发KEY_LONG_PRESS，转 WAIT_RELEASE
                    │松开(未到长按)▶ RELEASED_ONCE
RELEASED_ONCE ──300ms内再按下──▶ 发KEY_SHORT_PRESS_2(双击)，转 WAIT_RELEASE
              ──300ms超时未再按──▶ 发KEY_SHORT_PRESS_1(单击)，转 IDLE
WAIT_RELEASE ──松开──▶ IDLE
```

- **消抖本质**：不靠延时消抖，而是 20ms 周期轮询（TASK_PERIOD_MS=20）。抖动毛刺（<20ms）在一个采样周期内被状态机自然滤除——只有连续采样到按下才转移状态。
- **长短按判定**：PRESSED 态每周期 tick_count++，到 800ms/20ms=40 次触发长按；期间松开则进 RELEASED_ONCE。
- **双击判定**：RELEASED_ONCE 态里 300ms（15 周期）内再次按下 → 双击；超时 → 单击。代价是单击响应延迟 300ms（要等双击窗口结束才能确认），本项目无实时性要求，可接受。
- **事件传递**：扫描任务只往 xKeyQueue（深度 10）发"按键事件码"（1=单击/2=双击/3=长按），vKeyProcess 任务消费——扫描与处理分离，扫描周期稳定。
- 按键功能映射：单击点亮背光、双击打印任务栈信息（vTaskList + uxTaskGetStackHighWaterMark）、长按关闭背光（省电）。

### 追问：为什么双击窗口 300ms？单击为什么不能立刻响应？

> 双击和单击本质上冲突：单击要等"窗口期内没有第二次按下"才能确认，否则无法区分。300ms 是人体工程学经验值（太快用户来不及连按、太慢单击体验差）。若要单击即时响应，可用"短按立即响应 + 300ms 内二按改判双击"的事件覆盖方案，代价是处理逻辑复杂化。

## Q6.3 RTC 怎么配的？毫秒时间戳怎么来的？掉电时间保持吗？

### 答题要点（RTC_driver.c）

1. **时钟源**：LSE 外部 32.768kHz 晶振（比 LSI 内部 RC 精度高，日误差秒级 vs 分钟级）。启动流程：使能 PWR/BKPSRAM 时钟 → PWR_BackupAccessCmd → 查备份寄存器 BKP_DR1 是否 0xA5A5 判断是否首次配置 → 首次则 LSE 起振（带超时等待 LSERDY）→ 选 LSE 为 RTC 时钟源 → 使能 → 写保护解除 → EnterInitMode → 预分频配置 → 退出 → 等同步 → 恢复写保护 → 写 BKP_DR1=0xA5A5。
2. **分频**：AsynchPrediv=127、SynchPrediv=255 → 32768 ÷ 128 ÷ 256 = **1Hz** 秒脉冲；同步预分频计数器 0~255 每 1/256 秒翻转一次，就是**亚秒计数器**。
3. **毫秒时间戳（GetTimestamp）**：`milliseconds = ((255 - sub_seconds) × 1000) / 256`，与 RTC_GetTime 的时分秒拼成 `HH:MM:SS mmm`。所有 CAN 日志行都带这个时间戳。
4. **掉电保持**：RTC 和备份域由 VBAT 引脚独立供电（纽扣电池），主电源掉电后 RTC 继续走、BKP 寄存器内容保留——所以初始化标志 0xA5A5 判断"电池一直有电就不重新配置时间"。
5. **时间设置**：串口 `settime YYYY-MM-DD HH:MM:SS` 命令（Ymodem 命令行），RTC_SetDateTimeFromString 解析后写入，带参数合法性检查（时分秒、月日范围）。

### 追问：为什么读 RTC 时间前要 WaitForSynchro？

> RTC 运行在独立的 RTC 时钟域（LSE），主系统读 RTC 寄存器要跨时钟域同步，SYNC 位拉高才代表影子寄存器数据有效。初始化后和每次写之后都要等同步，否则读到旧值。

### 追问：亚秒计数器是递减的吗？

> 同步预分频计数器是从 255 递减到 0，减到 0 时秒进位。所以"已经过去的 1/256 秒" = 255 − 当前值，换算毫秒要 ×1000/256。

## Q6.4 正点原子 my_malloc 内存管理原理？为什么不用 libc 的 malloc？

### 答题要点（malloc.c）

- **原理**：分块内存池 + 内存表。把一块大内存（如内部 SRAM 128KB 的 SRAMIN 池）按最小块（MEM1_BLOCK_SIZE=32 字节，2 的幂）切分，用一张 uint16_t 内存表记录每块的"连续块数"（高 15 位）+ "占用标志"（最高位）。申请时首次适配：从表里找连续空闲块段，标记占用；释放时把标志清零。
- **三块内存池**：mem1=内部 SRAM（SRAMIN）、mem2=CCM RAM（0x10000000，只能 CPU 访问、DMA 不能用！）、mem3=外部 SRAM（0x68000000）。本项目只用了 SRAMIN。
- **为什么不用 libc malloc**：嵌入式裸机 libc 的 malloc 通常实现简单（或不可用）、碎片不可控、失败行为不可预期；自研内存表方案占用小、行为可预期、能统计使用率（my_mem_perused）。
- **关键注意点**（面试加分）：CCM RAM **不能做 DMA 缓冲**（DMA 总线到不了 CCM），所以 Ymodem 的发送缓冲、SD 卡的读写缓冲必须放 SRAMIN 不能放 CCM——这正是 my_malloc 要区分内存池的原因。

### 追问：my_malloc 有碎片问题吗？线程安全吗？

> 分块固定大小 + 首次适配也有碎片（小块申请交错释放后无法合并成大段）。线程安全：my_malloc 本身无锁，多任务并发调用需要外部保护（本项目业务分配都发生在任务初始化/单任务上下文，实际无并发调用，属潜在改进点）。

## Q6.5 LCD 显示任务怎么设计的？为什么 100ms 刷新一次？

### 答题要点（app.c vLCDDisplayTask）

1. **数据源**：lcd_display_queue（512 字节，元素 uint8_t），CAN 日志格式串 + 串口命令回显都往里投。
2. **两级缓冲**：任务内 buffer[512] 先把队列**排空**（xQueueReceive 超时 0，不阻塞），攒够 100ms 才统一解析刷新——屏幕刷新（SPI/并口写屏 + lcd_fill 清行 + lcd_show_string 写字）是毫秒级慢操作，逐条刷新会卡住任务且闪屏。
3. **滚动显示**：line_cache[14][41] 缓存 14 行 × 40 字符，满 14 行后整体上移一行（memcpy 搬移），新行写最后一行。非打印字符转成 `<XX>` 十六进制显示（保证乱码不破坏布局）。
4. **为什么 100ms**：人眼刷新舒适度与刷屏开销的平衡——太快刷屏占用 CPU 影响 CAN 解析，太慢信息滞后。100ms 下最坏信息延迟约 100ms，对监控场景足够。
5. **满度监控**：生产者侧（BMS27930_RecordTask）在投递前查 uxQueueSpacesAvailable，占用超 80% 打印警告——队列溢出风险的观测手段。

### 追问：队列 512 字节塞满了怎么办？

> 生产者用 xQueueSend(..., 0) 非阻塞投递，满则丢弃该字符（不是整行）。LCD 是"人看"的界面，允许丢部分显示数据，不能反压 CAN 收包链路。严重丢显示时靠 80% 警告发现，可增大队列。

## Q6.6 如果设备现场"不记录日志了"，你的排查思路？（情景题，高频）

### 答题要点（按"从现象到根因"分层，展示调试方法论）

1. **第一层：看指示灯/界面**。LED 是否闪烁（FreeRTOS 是否还活着）→ 不闪 = 死机/HardFault/低功耗误触发 → 连 SWD 看 PC 停在哪个 Handler，读 LR、PSR 反推异常来源。
2. **第二层：看串口输出**。串口有"Warning: SD card write queue full"→ 队列憋满，说明写盘路径堵死 → 往下查 SD 卡；串口有"Error: Failed to open/write"→ FatFs 层错误，查返回值（FR_NO_FILESYSTEM = 卡没格式化/损坏，FR_DISK_ERR = 底层读写错误）。
3. **第三层：SD 卡分层排查**。拔卡到 PC 上 fsck/chkdsk 查文件系统；换一张卡交叉验证（卡坏了 vs 驱动坏了）；挂逻辑分析仪看 CMD/DAT 线，CMD 有响应 = 链路活着，无响应 = 供电/时钟/引脚问题。
4. **第四层：CAN 侧排查**。看 LCD 有没有滚动新报文 → 没有 → 查 CAN：中断是否触发（断点打在 CAN1_RX0_IRQHandler）、过滤器配置是否被改、总线接线与终端电阻（CAN 总线两端必须各挂一个 120Ω 终端电阻，缺失会导致波形反射、报文错误重传直至总线错误状态）、can1_rx_lost_count 是否暴涨（队列满 → 任务饿死 → 查优先级被谁抢）。
5. **第五层：复位/降级验证**。重新上电是否恢复（瞬时故障）→ 恢复不了则缩小变量：注释掉 Ymodem 任务、只留 CAN→SD 最小链路二分定位。
- 方法论总结：**"分层排查 + 二分缩小 + 交叉验证"**，先区分"软件没收到/收到了没写/写了写坏"三层边界。

## Q6.7 HardFault 怎么排查？（必考基本功）

### 答题要点

1. **当场定位**：发生 HardFault 时看栈里压入的 PC、LR、xPSR（M4 异常入栈 8 个字），PC 指向出错指令，LR 判断是主程序还是中断里崩的。
2. **常见根因**（结合本项目经验）：
   - **野指针/未初始化全局**：本项目 main.c 注释明确——TaskHandle 定义位置不对导致初始化顺序问题报 hard 错误；
   - **栈溢出**：局部大数组（BMSRecord 任务里 ParseResult_t ~600B + 512B 缓冲）挤爆任务栈，覆盖相邻任务 TCB → 用 uxTaskGetStackHighWaterMark 排查；
   - **非对齐访问**：`uint32_t *p = (uint32_t*)&buf[1]` 之类（Cortex-M3/M4 不支持非对齐 LDR）；
   - **访问非法地址**：外设时钟没开就去读写寄存器（如忘了 RCC 使能 CAN 时钟）；
   - **除零**：M4F 无硬件除指令时除法走库函数，除数为 0 触发 UsageFault；
   - **中断里调阻塞 API / 优先级违规调 FromISR API**。
3. **系统化工具**：打开 MemManage/BusFault/UsageFault 三兄弟（默认被 HardFault 遮蔽，SCB->SHCSR 使能后能拿到更细分信息）、看 CFSR 寄存器的错误类型、加 configASSERT、打开栈溢出检测方法 2。

## Q6.8 你的代码为什么有 GBK 编码问题？怎么解决的？（项目真实事件）

### 答题要点

- 现象：Keil 编辑器里注释/LCD 中文字符串显示正常，但部分文件的中文出现乱码（或反向：编辑器乱码、运行正常）。
- 根因：Keil MDK 工程里不同源文件的编码不一致——部分文件是 GBK（Keil 默认），部分是 UTF-8（从别的编辑器/系统带进来），编辑器按错误编码解释就乱码；更麻烦的是**字符串字面量**按错误编码编译进固件，LCD 显示中文直接花。
- 解决：统一全部源文件编码（转成一种）+ 建立 `_gbk_backup/` 目录备份原始 GBK 文件防回归；验证方法：编译后看 LCD 实际显示 + 二进制里查字符串字节序。
- 教训（面试官爱听这个反思）：编码是"元数据"，跨工具链协作时要显式约定（文件头、.editorconfig）；不要在"显示正常"就停止——编辑器显示和运行时行为是两回事（记忆里的经典坑：editor display vs runtime behavior）。

## Q6.9 开放设计题：CAN 满载 3000 帧/秒全要落盘，你会怎么改？（综合设计题）

### 答题要点（展示架构能力，分四层讲）

1. **收包层**：加大 can1_rx_queue（10→128）；ISR 保持只拷贝；BMSRecord 任务**剥离解析**——收包任务只做"打时间戳 + 塞缓冲"，解析挪到独立的低优先级任务，收包绝不因解析变慢。
2. **缓冲层**：三级缓冲（队列→多扇区环形缓冲 64KB→SD 写任务），写盘慢时缓冲吸收突发，缓冲水位超阈值时降级策略（丢弃解析文本只存原始帧/丢弃低优先级报文）。
3. **写盘层**：多扇区连续写（一次 f_write 32KB 比 512B 效率高一个量级）；预分配固定大小文件（FAT 链不再动态分配，省掉 FAT 表反复改写）；写入用多缓冲 ping-pong 让 DMA 和 FatFs 并行。
4. **架构升级**：换 SPI NAND/eMMC + 专用文件系统（LittleFS/环形日志）；或引入"快慢存储"——先写 PSRAM/内部 Flash，空闲时再迁移到 SD 卡。
5. **算带宽**（面试官爱听"先算后设计"）：3000 帧/秒 × 每帧约 40 字节 = 120KB/s，4 位 SDIO 持续写 ~2MB/s 绰绰有余，瓶颈不在带宽在**写放大和随机小写**，所以核心是"攒批 + 连续写"。

## Q6.10 你项目里哪些地方用了"以空间换时间/以时间换空间"？（考察设计意识）

### 答题要点

- **以空间换时间**：
  - CAN 中断+队列（用 1KB RAM 换 ISR 微秒级退出）；
  - Ymodem CRC16 查表（256×2=512B 表换掉逐位运算）；
  - LCD 双缓冲 + 行缓存（RAM 换屏刷新平稳）。
- **以时间换空间/换寿命**：
  - SD 卡 512B/60s 批量写（用"最多 60 秒延迟"换 Flash 寿命和吞吐）；
  - 相同帧去重（用一次比对时间换日志体积）；
  - 软件定时器复用（LED+电池检测共用一个定时器回调，省一个任务）。
- 答这类题的关键：每说一个例子都带"换了什么、代价是什么"，体现工程权衡意识。

## 面试官可能挖的坑（本专题防翻车清单）

1. **"VBAT 通道为什么乘 2？"** → 内部 1/2 分压，实际电压 = 读数×2。不知道这点的会答出"参考电压 3.3V 12 位"就停。
2. **"Standby 前不请标志会怎样？"** → WU/SB 标志残留导致立即"虚假唤醒"或无法进入，代码里 PWR_ClearFlag 就是干这个的。
3. **"你的按键消抖时间多少？"** → 不是传统 10ms 延时消抖，是 20ms 轮询周期 + 状态机；能解释"为什么轮询周期本身即消抖"才是亮点。
4. **"CCM 能用来放 SD 卡的 DMA 缓冲吗？"** → 不能！CCM 不在 DMA 总线矩阵可达范围，放进去 DMA 传输直接失败/错数据。这是 F4 系列经典坑。
5. **"掉电日志最多丢多少？"** → 最多 60 秒（批量写兜底周期）+ FatFs 未 f_sync 的内部缓冲；主动承认并给改进方案。
6. **"为什么单击要等 300ms？"** → 与双击互斥的必然代价，答不上来说明没理解状态机本质。
7. **"你的 vTaskMonitor 为什么注释掉了？"** → 每 5 秒 vTaskList 走 printf 轮询发送，长任务列表打印会阻塞该任务几百 ms，长期运行时影响实时性；改为按键按需触发。
