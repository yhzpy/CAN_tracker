## 第一部分：基础概念扫盲

不懂这 8 个词，后面全是天书。先建立直觉：

| 概念 | 一句话理解 |
|------|-----------|
| **SDIO** | STM32 芯片里专门连 SD 卡的硬件模块，替你发命令、收数据，你只管配置它 |
| **CMD 命令 / DAT 数据** | SD 卡通信分两条线：**命令线**发指令（如"读第 100 块"），**数据线**传实际数据；两条线各有一套状态机（见 Q4.3） |
| **扇区（sector）** | SD 卡最小读写单位，固定 **512 字节**；哪怕只存 1 字节，也要操作一整个扇区 |
| **DMA** | "搬运工硬件"，让数据在 SD 卡与内存间自动搬运，**不占 CPU** |
| **FatFs** | 开源**文件系统**，把底层"扇区"包装成"文件/文件夹"，让你能用 `f_open/f_write` |
| **互斥量（Mutex）** | 一把"独占锁"，谁拿到谁用、别人排队等；用于**任务之间抢资源**，带优先级继承 |
| **信号量（Semaphore）** | 一个"事件通知"，常用于**中断告诉任务"我干完了"**；二值信号量只有 0/1 两态 |
| **写放大** | 为了写 40 字节日志，实际往卡里写了 512 字节甚至更多——"想写一点点、实际写一大堆"，既慢又折寿 |

## 第二部分：04 专题逐题讲解

### Q4.1　SD 卡初始化流程（11 步）

**问什么**：SD 卡上电不能直接用，要走一套"握手"流程。抓住主线即可，不用死背：

```
上电 → 复位卡(CMD0) → 问"你是2.0吗"(CMD8)
     → 反复问"初始化好了没"(CMD55+ACMD41 循环)
     → 读身份信息(CMD2 读 CID / CMD9 读 CSD 容量)
     → 分配地址(CMD3 拿 RCA) → 选中卡(CMD7)
     → 切 4 位宽总线提速(ACMD6) → 时钟从 400kHz 提到高速(≤25MHz)
```

三个高频追问：
- **为什么一开始时钟慢（400kHz）？** SD 规范硬性要求，初始化必须低速（老卡只认低速），确认支持高速后才提频。
- **为什么发 ACMD 前要先发 CMD55？** ACMD 不是独立命令，要先发 CMD55 声明"下一条按应用命令解释"，且只对**紧邻下一条**有效，所以循环里每轮都要重发。
- **74 个时钟脉冲干嘛？** 卡上电后内部要时间稳定，规范要求主机先空发 ≥74 个时钟让它"醒过来"。

### Q4.2　DMA 怎么配？为什么数据宽度用 Word（4 字节）？

**核心记这一个**：
> SDIO 的 FIFO 本身是 **32 位宽**，DMA 每次搬运必须一次搬 32 位、内存地址 4 字节对齐。配成字节/半字（8/16 位）宽度会对不齐、直接出错。

其他配置：DMA2 Stream3 + Channel4（SDIO 固定映射）；外设地址固定指向 `SDIO->FIFO`（不递增）、内存地址递增；读卡=外设→内存、写卡=内存→外设；优先级 VeryHigh（数据流不能断）；使能传输完成中断。

**追问"为什么不用 FIFO/Burst？"** → 简洁优先，48MHz 下带宽够用，复杂化没收益。

### Q4.3　CPSM / DPSM 双状态机（SDIO 最硬核）

- **CPSM**（命令路径状态机）：管**命令线**，发命令、收响应；
- **DPSM**（数据路径状态机）：管**数据线**，收发实际数据；两者独立。

**必记结论**：读写时要**先配好并使能 DPSM，再发命令使能 CPSM**。
**为什么？** 卡一收到读/写命令会**立刻**在数据线上送/取数据，数据路径没准备好就没人接 → 超时/CRC 错误。
**比喻**：命令是"开闸放水"，数据通道必须提前"站好位接水"。

### Q4.4　FatFs 是什么？分层结构？

**FatFs**：嵌入式开源 FAT 文件系统，RAM 占用小，移植只需实现 5 个底层函数（`disk_initialize/status/read/write/ioctl`）。

```
应用层    write_to_sd: f_open/f_write/f_close   ← 业务
   ↓
FatFs核心  ff.c: 管 FAT 表、目录、文件分配        ← 文件系统大脑
   ↓
适配层    diskio.c: disk_read/write → sd_read/write_disk  ← 翻译层
   ↓
SDIO驱动  sdmmc_read/write_blocks + DMA + 中断信号量      ← 硬件驱动
   ↓
硬件      SDIO 外设 → SD 卡
```

**关键设计**：适配层只管扇区读写、**完全不碰 FreeRTOS**；并发控制放在两个边界（应用层锁 + 驱动层锁，见 Q4.6）。

**追问**：`f_mount(fs,"0:",1)` 的参数 1 = "立即尝试挂载"；`f_open` 返回 `FR_NO_FILE` = 当天文件还没建，改用 `FA_CREATE_NEW` 新建（`app.c` write_to_sd 第 56-57 行）。

### Q4.5　为什么要"512 字节 / 60 秒批量写"？（项目最大亮点）

**每帧直接写的 4 个灾难**：
1. **写放大**：一帧日志才 40~80 字节，FatFs 一次至少写 512B 扇区 → 10 倍浪费；
2. **元数据放大**：`f_open`/`f_close` 每次都要"读-改-写" FAT 表和目录扇区，一次小追加背后是 3~4 次扇区操作；
3. **卡顿**：SD 卡内部编程 1~10ms 不可控，频繁写一直阻塞任务；
4. **折寿**：擦写次数有限（约 3000~10000 次），充电 4 小时约 28 万帧会把卡写废。

**两级缓冲方案**（`app.c` SDCard_WriteTask 第 322-367 行）：
- 第一级：解析任务把日志丢进队列 `xSDCardWriteQueue`（深度 3，每项 512B）；
- 第二级：任务内 `accumulate_buffer[512]` 累积，**攒满 512 字节（正好一扇区）或 60 秒无新数据**才写一次卡。

**追问**：
- *60 秒超时怎么实现？* 复用 `xQueueReceive` 的**超时参数**：`wait_time = 60s - 已过去时间`，收到数据就重置，超时返回就刷盘。不用软件定时器，因为"等数据"本就是任务的阻塞点。
- *深度为什么 3、每项为什么 512B？* 512B=一个扇区、与批量写粒度对齐；深度 3=1.5KB，能扛约 100ms 写盘阻塞，够用不浪费 RAM。

### Q4.6　双层同步机制（架构题，背这张表）

| 层 | 对象 | 类型 | 解决什么 |
|----|------|------|---------|
| **应用层** | `xSDCardMutex` + `g_sdio_mutex` | 互斥量 | **任务间抢卡**：写日志任务 vs Ymodem 导出任务，谁先拿到谁用整条 SD 链路 |
| **驱动层** | `g_sdio_transfer_sem` | 二值信号量 | **软硬件同步**：CPU 发完命令阻塞，等 DMA/SDIO 中断释放信号量才继续 |

**一句话**：上层管"谁用卡"，下层管"传完没"。互斥量有优先级继承、适合独占；二值信号量是"事件通知"、中断里 Give 安全。

**追问"为什么中断里不能 Give 互斥量？"** → 互斥量带优先级继承、**必须由持有它的任务释放**，中断里没有"任务持有者"概念，语义非法。中断→任务通知只能用信号量。

### Q4.7　SDHC 地址左移 9 位（经典坑 + 真 Bug）

> ⚠️ 本题细节较多，且 **04 文档本身的机制描述与修复建议都有误**，完整分析见 [第七部分](#第七部分q47-地址转换-bug-完整分析与修复)。此处先给结论：
> - 标准容量卡（SDSC）用**字节地址**、高容量卡（SDHC/SDXC）用**块地址**；`<<9`=×512、`>>9`=÷512。
> - 代码分两层换算，SDSC v2.0 与 SDHC 都正确，但 **SDSC v1.1 因上层条件 `!= V1_1` 被漏掉，寻址偏差 512 倍（真 Bug，已修复）**。
> - **正确修复是上层无条件 `<<= 9`**，不是 04 文档说的 `!= HIGH_CAPACITY_SD_CARD`（那样反而写坏 SDHC）。

### Q4.8　为什么写卡要用互斥量？两个任务同时写会怎样？

- **FatFs 默认非线程安全**：FAT 表、目录缓存、文件对象都是共享状态，并发 `f_write`/`f_open` 会搞乱 FAT 链 → 文件损坏、数据交叉、甚至分区读不出。
- 两个并发方：**SDCard_WriteTask（写日志）** + **Ymodem_Task（读文件导出）**，都先抢 `xSDCardMutex` 再操作。
- **为什么用互斥量而非关中断？** 文件操作几十 ms，关中断会长时间禁调度、丢 CAN 包；互斥量让等待任务"睡着排队"，CPU 让给别人。

**追问"Ymodem 传输时日志会饿死吗？"** → 不会死锁。`Ymodem_SendFile` 在等接收端 'C' 的 30 秒窗口里**主动释放互斥量**，真要读数据时再重新获取——长等待期间日志照写（刻意的锁粒度设计）。

### Q4.9　掉电瞬间正在写卡会怎样？怎么改进？

- **风险**：扇区写一半掉电→扇区损坏；FAT 表更新一半→文件链断裂（"文件在但读不出"）；目录项没写完→文件丢失。
- **现状**：512B/60s 批量写已把危险窗口压到最小，但 `write_to_sd` 没调 `f_sync`，数据可能停在 FatFs 内部缓冲没落盘。
- **改进方向**：① 每次 `f_write` 后加 `f_sync` 强制刷盘；② 用已有 VBAT ADC 做掉电检测，低压就停写、完成当前扇区、`f_close`；③ 双文件轮换 + 环形日志，坏了只影响一段。

## 第三部分：防翻车清单

面试官用来识别"背项目的人"的问题，记结论：

1. **SDHC 地址直接传扇区号吗？** → 不是，要 ×512（<<9），只有 v1.1 不乘（**注意：这恰是 Bug 所在，见第七部分**）。别答反。
2. **f_write 是原子操作吗？** → **不是**，会拆成多次扇区 I/O，中途被打断数据不一致，必须用互斥量保护整段 open-write-close。
3. **测过写速度吗？** → 4 位总线 24MHz 理论 12MB/s，实际连续写 2~5MB/s，随机小写掉到几百 KB/s——正好证明批量写必要。
4. **为什么不用 exFAT？** → 嵌入式一般选 FAT32：兼容性最好、实现小、无专利包袱。
5. **队列占多少内存？** → 3×512 = **1.5KB**，从 FreeRTOS 的 30KB 堆里出，要能当场算。
6. **DMA 缓冲为什么 4 字节对齐？** → SDIO FIFO 是 32 位宽，Word 传输要求内存 4 对齐（见第四部分）。
7. **写超时设多少？超时怎么办？** → 3000ms，超时置错误标志 + 错误计数、返回 SD_ERROR；目前**没有自动复位重试**（主动说这是可改进点）。

## 第四部分：深入专题一 —— 内存地址对齐

### 定义
把数据存放在"自己大小的整数倍"地址上：
- 4 字节数据（`int`/Word）放地址能被 4 整除处（0、4、8…）；
- 2 字节数据（`short`/半字）放能被 2 整除处；
- 1 字节（`char`）放哪都行。

**"4 字节对齐" = 地址 % 4 == 0。**

### 为什么要对齐（核心原因）
CPU/硬件访问内存不是一个字节一个字节读，而是**一次读一个固定宽度的块**。比喻：内存像一排储物柜，硬件每次只能"整格整格"开柜。

```
✅ 对齐(地址=4)：  [   ][XXXX][   ]   硬件一次读 4~7 → 一步搞定
❌ 不对齐(地址=5)：[   ][XX|XX][   ]  数据横跨两块 → 读两次再拼接，慢，甚至硬件异常
```

### 回到项目（重点）
> SDIO 的 **FIFO 是 32 位（4 字节）宽**，DMA 配成 **Word 传输**，每次搬 4 字节。若缓冲区起始地址不是 4 的倍数，数据没法整齐落地 → 传输错位/报错。

所以 Q4.2 的"数据宽度用 Word"和"缓冲 4 字节对齐"是**同一件事的两面**：宽度规定"一次搬 4 字节"，对齐保证"这 4 字节能整齐落地"。FatFs 传下来的一般是 512B 自然对齐块（512 是 4 的倍数），天然满足；自己 `malloc` 给 DMA 用时要留意。

### 延伸：结构体因对齐"偷偷变大"
```c
struct A { char c; int i; };   // 你以为 sizeof=5，实际=8！
```
编译器为让 `int` 落在 4 的倍数地址，在 `char` 后插入 **3 字节 padding**：
```
偏移:  0    1    2    3    4    5    6    7
      [c ][填充 填充 填充 ][ i   i   i   i  ]
```
**项目意义**：队列元素 `SDCardWriteData_t`、CAN 帧 `Can1RxFrame` 都是 struct，实际大小会因填充比手算的大；算内存/队列深度时要留意（清单第 5 条 3×512=1.5KB 之所以可控，是因为里面用 `char` 数组，char 不产生填充）。

### 小结
| 要点 | 内容 |
|------|------|
| 定义 | 数据放在"自身大小整数倍"地址上 |
| 4 字节对齐 | 地址 % 4 == 0 |
| 根本原因 | 硬件一次读一个固定宽度的块，对齐才能一次搞定 |
| 不对齐后果 | 慢（读两次拼接）或硬件异常 |
| 项目场景 | SDIO FIFO 32 位宽 + DMA Word 传输 → 缓冲必须 4 字节对齐 |
| 副作用 | 结构体因 padding 变大，`sizeof` 可能超预期 |

## 第五部分：深入专题二 —— g_sdio_transfer_sem 如何工作

### 它是什么
`g_sdio_transfer_sem` 是**二值信号量**（`sdio_sdcard.c` 第 13 行定义，第 150 行 `xSemaphoreCreateBinary()` 创建）。"二值"=只有 0/1 两态，本质是一个"事件旗标"。

**唯一职责**：解决**软件（任务）与硬件（SDIO 中断）的同步**——任务发完读写命令后不知道硬件何时干完，就靠它"睡等"，中断干完再"叫醒"。

### 为什么需要它
SD 卡写块，CPU 发完 CMD25 后实际搬运由 SDIO+DMA 后台完成，需几毫秒：
- ❌ **死等（轮询）** `while(!完成);`：CPU 干等、纯浪费；
- ✅ **信号量阻塞** `xSemaphoreTake`：任务睡过去，**CPU 立刻让给别的任务**（CAN 收包、LCD 刷新），中断干完再唤醒。

这就是 Q4.6 说的"下层管传完没"。

### 完整工作流程（核心闭环，以写卡为例）
```
【任务侧 sdmmc_write_blocks】(第836-887行)
① 清标志 g_sdio_transfer_end=0, g_sdio_error=SD_OK   (837-839)
② 配 DMA、配 DPSM 数据路径                            (843-849)
③ 使能 SDIO 中断 DATAEND/DTIMEOUT/DCRCFAIL/TXUNDERR   (852)
④ 发 CMD25 命令 → 硬件开始搬数据
⑤ xSemaphoreTake(g_sdio_transfer_sem, 3000ms) ← 睡等  (855)
                    ⋮ （CPU 去跑别的任务）
【中断侧 SDIO_IRQHandler】数据传完触发               (1316)
⑥ 判 DATAEND → g_sdio_transfer_end=1
⑦ xSemaphoreGiveFromISR(g_sdio_transfer_sem,...) ← 叫醒 (1337)
⑧ portYIELD_FROM_ISR(...) ← 需要则立即切任务         (1388)
                    ⋮
【任务侧被唤醒，从 855 继续】
⑨ 关中断、关 DMA                                     (865-869)
⑩ 查 g_sdio_transfer_error：无错返回成功、有错返回错误码 (872-875)
```
一句话：**任务 take 睡等 → 硬件传完中断 give 叫醒 → 任务醒来查结果。**

### 5 个必须知道的细节（面试爱挖）
1. **只有 SDIO 中断 give，DMA 中断不 give**：`DMA2_Stream3_IRQHandler`（第 1396-1412 行）只清标志、置错误位，**不释放信号量**。代码注释点明：`DMA完成不代表SDIO完成，由SDIO中断处理`。真正代表"块传输结束"的是 SDIO 的 DATAEND 中断。（注意：04 文档写"SDIO/DMA 中断释放信号量"不严谨，**实际只有 SDIO 中断释放**。）
2. **成功和失败都 give**：DATAEND（成功）、DTIMEOUT、DCRCFAIL、RXOVERR、TXUNDERR 这 5 个分支**都调了 `xSemaphoreGiveFromISR`**。错误分支先置 `g_sdio_transfer_error=1`+错误码再 give，任务醒来查标志即知成败；若不 give，任务会白等到 3000ms 超时。
3. **Take 带 3000ms 超时兜底**：`pdMS_TO_TICKS(SDIO_TRANSFER_TIMEOUT_MS)`，中断异常没来时任务不会永久卡死，超时关中断/DMA 返回 `SD_DATA_TIMEOUT`（防御性设计）。
4. **`xHigherPriorityTaskWoken` + `portYIELD_FROM_ISR`**：FreeRTOS 中断释放信号量的标准套路，记录是否叫醒了更高优先级任务，需要则在中断退出时**立刻切换**而非等下一个 tick，降低延迟。
5. **为什么中断能用 GiveFromISR 却不能碰互斥量**：二值信号量是纯"事件通知"、有 `FromISR` 版本，中断 give 安全；互斥量带优先级继承 + 必须持有者释放，中断无持有者概念，非法。

### 小结表
| 维度 | 内容 |
|------|------|
| 类型 | 二值信号量（0/1 事件旗标） |
| 创建 | `xSemaphoreCreateBinary()`，SD 初始化时 |
| Take（等） | 任务侧 `sdmmc_read/write_blocks`，带 3000ms 超时 |
| Give（放） | **仅** `SDIO_IRQHandler`，成功与 5 种错误分支都 give |
| DMA 中断 | 只标错误，**不** give（DMA 完成 ≠ SDIO 完成） |
| 唤醒后 | 任务查 `g_sdio_transfer_error` 判成败 |
| 本质 | 软硬件同步：任务睡等、中断叫醒，CPU 不空转 |

## 第六部分：深入专题三 —— 锁 vs 信号量，谁拿谁还

### 常见误区（本次对话纠正过的）
> 误："DMA 开始传输就拿锁，SDIO 收完后中断还锁。"

这句话**把"锁"和"信号量"混为一谈了**。这里是**两个独立对象**，拿/还的人完全不同：

| 对象 | 类型 | 谁 Take（拿/等） | 谁 Give（还/放） |
|------|------|----------------|----------------|
| `g_sdio_mutex` | **互斥量（锁）** | **任务** | **任务**（中断从不碰它！） |
| `g_sdio_transfer_sem` | **二值信号量（事件旗标）** | **任务**（睡等） | **SDIO 中断** |

### 完整时间线（谁在哪步做什么）
```
【任务】sd_write_disk 入口
  ├─① xSemaphoreTake(g_sdio_mutex)   ← 任务拿"锁"(传输还没开始就先拿)  (1461)
  ├─② 地址换算 lsaddr <<= 9
  ├─③ 进入 sdmmc_write_blocks
  │     ├─ 配 DMA、配 DPSM、使能 SDIO 中断、发 CMD25 ← 硬件此刻才搬数据
  │     ├─④ xSemaphoreTake(g_sdio_transfer_sem) ← 任务拿"信号量"=睡等   (855)
  │     │        ⋮ （任务睡着，CPU 跑别的）
  │     ├─【SDIO 中断】⑤ xSemaphoreGiveFromISR(g_sdio_transfer_sem) ← 中断放"信号量" (1337)
  │     │        ⋮ （叫醒任务）  ← 注意：中断并没有动 g_sdio_mutex！
  │     └─⑥ 任务醒来：关中断/DMA、查错误、返回
  └─⑦ xSemaphoreGive(g_sdio_mutex)   ← 任务还"锁"(整个传输都结束才还)  (1471)
```

### 直接结论
- **锁（`g_sdio_mutex`）拿得更早**：任务刚进 `sd_write_disk` 入口就拿了，那时 DMA 还没配、命令还没发。它保护的是**整段扇区操作**（地址换算 + 配 DMA + 发命令 + 等传输 + 查错误），不只保护 DMA 那一下。
- **中断根本不碰锁**：中断 give 的是**信号量**（叫醒睡等任务）；**锁是任务自己醒来、处理完、返回到函数末尾时自己还的**。

### 为什么这样设计
- **锁必须"谁拿谁还"**：有优先级继承，中断无"任务持有者"概念，中断 give 互斥量非法（呼应 Q4.6）。
- **信号量才允许"中断 give"**：纯事件通知，有 `FromISR` 版本，安全。

> **一句话总结**：锁 = 任务传输前拿、传输后还，圈住"谁能用这张卡"；信号量 = 任务睡等、中断叫醒，回答"这一次传完没有"。中断只放信号量，从不碰锁。

## 第七部分：Q4.7 地址转换 Bug 完整分析与修复

> 这是最经典、最能加分的一题，也是**本次真正改了代码**的地方。特别注意：**04 文档在本题的机制描述和修复建议都有误**，下面以真实代码为准重新推导。

### 7.1 背景：三种卡的"地址"含义不同

SD 卡按容量分三类（枚举见 `sdio_sdcard.h` 第 257-259 行）：

| 卡类型 | 宏 | 值 | 容量 | CMD17/24 参数含义 |
|--------|-----|----|------|-----------------|
| SDSC v1.1 | `STD_CAPACITY_SD_CARD_V1_1` | **0** | ≤2GB | **字节地址** |
| SDSC v2.0 | `STD_CAPACITY_SD_CARD_V2_0` | **1** | ≤2GB | **字节地址** |
| SDHC/SDXC | `HIGH_CAPACITY_SD_CARD` | **2** | ≥4GB | **块地址**（512B 为单位） |

- **标准容量卡（SDSC）**用**字节地址**——"从第 51200 字节开始读"；
- **高容量卡（SDHC）**用**块地址**——"读第 100 块"。
- FatFs 传下来的永远是 **LBA 扇区号**。`<<9`=×512（扇区号→字节地址），`>>9`=÷512（字节地址→块号）。

### 7.2 代码里的两层换算

**上层**（FatFs 适配层）`sd_read_disk`/`sd_write_disk`，修复前：
```c
if (CardType != STD_CAPACITY_SD_CARD_V1_1) lsaddr <<= 9;   // 除 v1.1 外都左移
```

**下层**（核心块读写）`sdmmc_read_blocks`（第 682-686 行）/`sdmmc_write_blocks`（第 779-783 行）：
```c
if (CardType == HIGH_CAPACITY_SD_CARD) {   // 只有高容量卡
    blksize = 512;
    addr >>= 9;                            // 右移还原成块号
}
```

**下层的隐含约定**：它认为传进来的 `addr` 是**字节地址**，自己负责"如果是 SDHC 就 >>9 转块号"。所以下层期望上层交给它的一定是 **字节地址 = LBA × 512**。

### 7.3 三种卡完整追踪（真相表，修复前）

设 FatFs 传下 LBA 扇区号 = `S`：

| 卡类型 | 上层 `!=V1_1 → <<9` | 下层 `==HIGH → >>9` | 最终 CMD 地址 | 卡期望 | 结果 |
|--------|:---:|:---:|:---:|:---:|:---:|
| **SDSC v1.1** (0) | 0≠0 **假**→不移 = `S` | 0≠2 假→不移 = `S` | `S` | 字节地址 `S×512` | ❌ **差 512 倍** |
| **SDSC v2.0** (1) | 1≠0 **真**→`S×512` | 1≠2 假→不移 = `S×512` | `S×512` | 字节地址 `S×512` | ✅ |
| **SDHC** (2) | 2≠0 **真**→`S×512` | 2==2 **真**→`S` | `S` | 块地址 `S` | ✅ |

**注意 SDHC 行**：上层先 ×512、下层再 ÷512，**绕一圈回到扇区号 `S`**，正好等于 SDHC 要的块地址，所以正确。

> ⚠️ **纠正 04 文档**：文档说"SDHC：上层不移位（保持扇区号）"——**与真实代码不符**。真实代码里 SDHC 在上层是**移了的**（2≠0 为真），只是下层又移回来。结论（SDHC ✓）没错，但机制描述错了。面试要按真实代码讲。

### 7.4 真正的 Bug：SDSC v1.1 卡读写错位

真相表第一行：**SDSC v1.1 两层都不移位**，扇区号 `S` 被直接当字节地址传给命令，但 v1.1 期望字节地址 `S×512`。

- **后果**：想读第 `S` 个扇区，实际读到第 `S/512` 字节位置——**寻址偏差 512 倍**，数据完全错乱。
- **根因**：上层用 `!= STD_CAPACITY_SD_CARD_V1_1` 做条件，等于**专门把 v1.1 排除在左移之外**，而 v1.1 恰恰最需要左移（字节寻址）。

### 7.5 ⚠️ 04 文档给的"修复方案"本身是错的

04 文档 Q4.7 建议改成：
```c
if (CardType != HIGH_CAPACITY_SD_CARD) lsaddr <<= 9;   // 文档的建议（错误！）
```

**顺着代码验证，这个改法会把 SDHC 写坏**：

| SDHC(2) 用文档改法 | 结果 |
|---|---|
| 上层 `2 != 2` **假** → 不移位 = `S` | |
| 下层 `2 == 2` **真** → `S >> 9` = `S/512` | ❌ 传给 CMD 的是 `S/512`，SDHC 却期望块号 `S` |

SDHC 直接被搞坏（差 512 倍，方向与原 Bug 相反）。文档的建议基于"下层不移位"的单层思维，与代码里**下层实际有 `>>9`** 的现实冲突。

### 7.6 真正正确的修复（已落地）

既然下层约定"进来的必须是字节地址、它自己会对 SDHC 右移还原"，那上层就该**无条件左移**：
```c
long long lsaddr = saddr;
lsaddr <<= 9;   // 无条件：LBA 扇区号 → 字节地址，交给下层按卡类型决定是否 >>9
```

**验证（三种卡全过）**：

| 卡类型 | 上层无条件 `<<9` | 下层 `==HIGH → >>9` | 最终 | 期望 | 结果 |
|--------|:---:|:---:|:---:|:---:|:---:|
| SDSC v1.1 | `S×512` | 不移 `S×512` | `S×512` | 字节 `S×512` | ✅ |
| SDSC v2.0 | `S×512` | 不移 `S×512` | `S×512` | 字节 `S×512` | ✅ |
| SDHC | `S×512` | 移回 `S` | `S` | 块 `S` | ✅ |

**面试怎么讲**：先说"我发现 v1.1 卡被漏掉、寻址差 512 倍"，再说"修复要联系下层一起看——下层已对 SDHC 右移，所以上层应无条件左移，而不是像直觉那样加 `!= HIGH_CAPACITY` 判断，那样反而破坏 SDHC"。这样能体现你**真把两层代码串起来审过**，是极强加分项。

### 7.7 连注释都是错的

修复前 `sd_write_disk` 第 1462 行注释：
```c
//高容量SD卡（SDHC/SDXC，≥4GB）使用字节地址而非扇区地址，需要左移9位（乘以512）
```
**这句把事实说反了**：高容量卡（SDHC）用**块地址**，标准容量卡（SDSC）才用**字节地址**。注释错 + 条件错，两处叠加导致 v1.1 漏网。

**面试价值**：主动指出"我代码里这句注释本身就是错的、事实恰好相反，所以我没盲信注释，而是拿 SD 协议规范交叉验证"——直接展示代码审查能力与严谨性。

### 7.8 调试这类地址问题的方法

1. **逻辑分析仪抓 CMD 线**：看 CMD17/CMD24 实际参数值，与期望的字节/块地址对比；
2. **发 CMD13 读卡状态**：看 `ADDRESS_ERROR` 位是否置起；
3. **对照实验**：同位置连续读两次结果不一致、写后读回内容错位 512 倍，都是地址换算问题典型症状；
4. **换卡复现**：只有 v1.1 老卡（≤2GB）才触发此 Bug，SDHC 卡测不出——需针对性找老卡验证。

### 7.9 追问：SDHC 容量怎么从 CSD 算

- **CSD v2.0（SDHC）**：`C_SIZE` 是 22 位，`容量 = (C_SIZE + 1) × 512KB`，代码 `CardCapacity = (DeviceSize + 1) * 512 * 1024`；
- **CSD v1.0（SDSC）**：`容量 = (C_SIZE+1) × 2^(C_SIZE_MULT+2) × 2^READ_BL_LEN`。

## 本次对话经验总结（可复用）

1. **分层驱动的地址换算要"两层合起来看"**：上层与下层可能各做一次移位，单独看任一层都会得出错误结论；必须把"FatFs 的 LBA → 上层 → 下层 → CMD 参数"整条链追踪一遍。
2. **不要盲信注释，也不要盲信文档**：本次同时发现"代码注释写反"和"04 文档的机制描述+修复建议都错"两处问题，最终**以真实代码逐行推导为准**。
3. **提修复方案前要顺代码验证**：直觉的 `!= HIGH_CAPACITY` 改法看似合理，实则破坏 SDHC；正确解要匹配下层的既有约定（下层期望字节地址）。
4. **锁与信号量职责分明**：互斥量=任务拿任务还（圈资源），二值信号量=任务等中断放（报事件）；中断永远不碰互斥量。
5. **DMA/外设宽度决定对齐要求**：SDIO FIFO 32 位宽 → DMA Word 传输 → 缓冲 4 字节对齐，三者是一条因果链。
