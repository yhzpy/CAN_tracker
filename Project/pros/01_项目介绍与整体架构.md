> 这一部分决定面试官的第一印象。目标：2 分钟内把项目讲清楚，并把话题引导到你准备好的领域。

## Q1.1 简单介绍一下你的项目（100% 必考，第一题）

### 答题要点（按这个结构讲，控制在 2 分钟）

1. **一句话定位**：这是一个基于 STM32F407 的 CAN 报文记录仪（CAN Tracker），挂在电动汽车直流充电桩的 CAN 总线上，监听 BMS（电池管理系统）和充电机之间的 GB/T 27930 充电通信报文。
2. **它做什么**：实时采集、解析协议、LCD 显示关键参数、SD 卡按天记录 CSV 日志、串口命令 + Ymodem 协议导出日志到 PC。
3. **技术栈**：STM32F407（SPL 标准库）+ FreeRTOS（9 个任务）+ CAN（中断+队列）+ FatFs/SDIO+DMA（SD 卡）+ USART DMA 空闲中断 + GB/T 27930-2015 协议解析。
4. **我的职责**：全部代码独立完成——从底层驱动（CAN/SDIO/串口）到协议解析到应用任务框架。
5. **亮点收尾**（主动抛出，引导提问方向）：
   - SD 卡写入做了"512 字节/60 秒"批量缓冲策略，避免频繁小写写坏 SD 卡；
   - 协议解析做了"相同帧去重"，大幅降低日志冗余；
   - 串口用 DMA 循环接收 + 空闲中断 + 任务通知，CPU 几乎不参与搬运。

### 参考话术

> "这个项目是一个电动汽车充电报文记录仪。充电时 BMS 和充电机之间会通过 CAN 总线交互 GB/T 27930 协议报文，我的设备并接在这条总线上，以 250kbps 监听所有报文。数据进来后分两条路：一条解析成中文描述实时显示在 LCD 上；另一条带时间戳写入 SD 卡 CSV 文件，按天分文件。事后可以通过串口命令行把日志用 Ymodem 协议下载到电脑分析。整个软件跑在 FreeRTOS 上，共 9 个任务，CAN 收包用中断加队列，SD 写入做了批量缓冲优化。"

### 面试官可能追问

**追问：这个项目是实际产品还是学习项目？解决什么痛点？**
> 定位是"充电过程故障排查工具"：当充电失败或车辆报错时，现场工程师需要完整的报文证据链来定位是车端还是桩端的问题。传统做法是用 PC 加 USB-CAN 盒子采集，但这个设备可以长时间独立挂在现场，自带时间戳和持久化存储，事后导出分析。

## Q1.2 画出你的系统架构图，讲讲数据流

### 答题要点（照着 README 里的链路图讲，注意讲"每一级为什么存在"）

```
CAN总线 ──(CAN1_RX0中断)──▶ can1_rx_queue(深度10) ──▶ BMS27930_RecordTask(优先级3)
                                                          ├── 解析+去重 ──▶ xSDCardWriteQueue(深度3) ──▶ SDCard_WriteTask ──▶ FatFs ──▶ SDIO+DMA ──▶ SD卡
                                                          └── 格式化 ──▶ lcd_display_queue(512B) ──▶ vLCDDisplayTask(100ms刷新) ──▶ LCD
串口链路：USART1 ──(DMA循环+IDLE中断)──▶ 任务通知 ──▶ vUART1Task ──▶ ymodem_rx_queue ──▶ Ymodem_Task ──▶ 命令行/Ymodem传输
```

讲解要点：
- **两级队列解耦**：中断只做"搬运到队列"，任务只做"从队列取"，中断执行时间可控（微秒级）；CAN 收包任务和 SD 写任务速度不匹配，靠队列缓冲。
- **生产者消费者分离**：解析任务（生产者）永远不被慢速的 SD 写（消费者）阻塞，队列满时选择"丢包并计数"而不是死等。
- **为什么 SD 写单独一个任务**：FatFs 写文件可能要等 SD 卡编程（几十 ms），如果和 CAN 解析放一个任务，CAN 队列会被憋满丢包。

## Q1.3 这个项目最大的难点是什么？你是怎么解决的？

### 答题要点（选 2~3 个讲，每个都要"问题→方案→效果"）

**候选 1：SD 卡写入寿命问题（推荐首选，讲得最清楚）**
- 问题：充电过程持续数小时，周期报文每帧都写 SD 卡会产生海量小写入——FatFs 每次 f_write 至少改一个 512B 扇区，还会更新 FAT 表和目录项，写放大严重，SD 卡（NAND Flash）很快报废。
- 方案：应用层做了两级缓冲——解析任务只把日志塞进队列（每项 512B），独立的 SDCard_WriteTask 在任务内累积满 512 字节（恰好一个扇区）或者 60 秒无新数据时才调一次 f_write，写时用互斥量保护。
- 效果：写次数降低约两个数量级，一次写一个整扇区也减少了 FatFs 的读写放大。

**候选 2：协议解析的报文去重**
- 问题：充电稳态时 BCL（充电需求）、BSM（电池状态）等周期报文内容变化很小，逐帧完整解析记录会产生大量重复日志。
- 方案：BMS27930_RecordTask 里用静态变量记住上一帧的 extId/DLC/data，新帧先逐字节比对，完全相同的只记录原始 hex（时间戳+ID+数据），不同的才走完整解析并更新"上一帧"。
- 效果：日志体积显著减小，同时保留每一帧的原始证据（不能丢数据）。

**候选 3：串口"空闲中断 + 任务通知"框架**
- 问题：命令交互式串口既要收 Ymodem 命令，又要收 Ymodem 传输的数据块，长度不定，逐字节中断会淹没 CPU。
- 方案：USART1 用 DMA 循环模式搬数据到环形缓冲区，CPU 完全不参与；总线空闲触发 IDLE 中断，在中断里算好长度、重启 DMA、发任务通知；vUART1Task 用 ulTaskNotifyTake 阻塞等待，被唤醒后一次性处理整包数据。
- 效果：任意长度数据包都能接收，CPU 只在一帧结束时被唤醒一次。

### 追问：过程中有没有踩过什么印象深刻的坑？

参考答案（选讲，必须真实且能展开）：
- **SD 卡地址换算坑**：SDHC/SDXC 卡（≥2GB）的读写地址是"字节地址"（扇区号×512），而 SDSC v1.1 老卡用"字节地址=扇区号"（其实 SDSC 直接用字节地址，卡内部按 CSD 的块长解释）。代码里 `if (CardType != STD_CAPACITY_SD_CARD_V1_1) lsaddr <<= 9;`，一开始漏了这个判断，老卡能用、SDHC 卡完全读不出来，用逻辑分析仪看 CMD 参数才定位。详见 [04_SD卡存储与FatFs拷打](./04_SD卡存储与FatFs拷打.md) Q4.8。
- **编码坑**：Keil 工程文件的编码（GBK/UTF-8）不一致导致中文注释和 LCD 中文显示乱码，后来统一了文件编码并做了 GBK 备份目录。详见 [06_工程细节与综合拷打](./06_工程细节与综合拷打.md) Q6.9。

## Q1.4 如果让你重新设计这个项目，你会改什么？（开放题，考察反思能力）

### 答题要点（挑 3 条，展示工程思维）

1. **存储层换"环形日志 + 预分配文件"**：当前每天一个文件无限追加，长期运行会写满卡。改进：预分配固定大小日志文件，写满后覆盖最旧的（环形），或者按容量触发"最旧文件删除"，并加 f_sync 定期刷盘防掉电丢数据。
2. **CAN 接收防丢包**：当前队列深度 10、满了就丢，只在调试计数。改进：加大队列并增加"流控"——统计丢包率，超过阈值降级为"只记原始 hex 不解析"模式；或用双缓冲 + 事件组唤醒代替单队列。
3. **协议解析表驱动化**：当前 19 种报文用 switch-case + 19 个函数，可改为"ID→解析器"查表 + 字段描述表驱动，新增报文只加数据不改逻辑；解析结果用二进制格式（而非 sprintf 字符串）存储，日志体积再降一个量级。
4. **低功耗更彻底**：当前只有 VBAT 过低进 Standby，可加 RTC 定时唤醒 + 按键唤醒的 STOP 模式，把待机电流从 mA 级降到 μA 级。
5. **可靠性**：加看门狗（IWDG）、上电 SD 卡异常时的降级策略（无卡也能跑显示和串口）、Flash 掉电保护。

## 面试官可能挖的坑（本专题防翻车清单）

1. 被问"波特率多少"：答 **250kbps**（GB/T 27930 规定值），并当场默算 42M/((1+6+7)×12)=250k，注意 main.c 里 brp 参数是 **12**，不是注释示例里的 6。
2. 被问"栈大小"：必须说清单位是**字**，512 字 = 2KB。
3. 被问"中断优先级为什么是 5、6"：因为 NVIC_PriorityGroup_4（全抢占），configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5，**数值 ≥5 的中断才能安全调用 FreeRTOS 的 FromISR API**。CAN(5)、DMA2_Stream3(5)、USART1(6)、SDIO(6) 都满足。
4. 被问"队列满了怎么办"：本项目策略是**丢新包 + 计数**（CAN 队列、LCD 队列），SD 写队列满则打印警告。要能解释为什么选丢包而不是阻塞——解析任务阻塞会连带 CAN 队列憋满，丢最新报文比丢全部更可接受。
5. 被问"项目几个人做/多长时间"：提前想好一致的回答（建议：个人独立完成，周期约 X 周/X 月，分驱动移植→协议解析→存储→界面→联调五个阶段）。
